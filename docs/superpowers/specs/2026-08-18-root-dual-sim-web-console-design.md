# Root 双卡、低延迟与本地控制台设计

## 目标

- 双卡设备中，每个已观测到的 SIM 槽位都形成独立档案，分别维护接收手机号。
- 短信到达 Android 后尽快读取并上传，管理台自动看到新消息。
- Root 模块提供本机配置控制台，避免通过 ADB 手改 `config.json`。

## 已确认根因

- Root 运行时已从真实短信识别出 `slot 0/subscription 5` 和 `slot 1/subscription 6`。
- 后端只有在 Android 同时返回手机号时才创建自动 SIM 档案；当前 ROM 将号码隐藏，因此第二张卡没有档案。
- 管理台新增手机号把槽位固定为 `0`，导致只能维护一个号码。
- 手机配置轮询间隔是 15 秒，服务还会在读取和上传后才进入下一轮；数据库实测新短信入库延迟约 20-21 秒。
- 管理台没有自动刷新，进一步放大了用户看到的延迟。
- `sms-relay-wake` 只创建标记文件，现有服务循环没有消费该标记。

## 双卡档案

每次接收短信时，只要事件包含非负 `sim_slot`，后端就创建或更新对应的自动 SIM 档案。档案可以没有手机号，但保留 `slot_index`、`subscription_id`、运营商和更新时间。自动更新不得覆盖手动手机号，也不得把手动来源改回自动来源。

现有数据库通过受控的历史修复读取消息中的 `sim_slot` 和加密 metadata，补出已观测槽位。管理台显示 `SIM 1`、`SIM 2`、内部订阅号和脱敏手机号；每一行单独编辑手机号。新增按钮选择第一个尚未存在的槽位，不再固定写槽位 0。

## 低延迟

Root 模块默认轮询改为 3 秒。服务等待使用一秒粒度的可中断等待：检测到 `run/telephony.changed` 或 `run/config.changed` 时立即进入下一轮，消费标记后执行读取。等待过程只执行文件存在性检查和 `sleep 1`，不忙等。

管理台连接后每 2 秒刷新设备、消息和验证码；刷新请求不得覆盖正在编辑的 SIM 表单，也不得持续显示“处理中”。手动刷新保持不变。

验收指标以平台数据库的 `created_at - received_at` 为准。在手机短信 Provider 已可见且本地网络正常时，目标延迟为 3-5 秒。

## 本地配置控制台

控制台由现有 Go runtime 的 `web` 子命令提供，只绑定 `127.0.0.1:35000`。它不随开机常驻；Root 管理器执行 `action.sh` 无参数或 `action.sh web` 时启动服务并用 Android `am start` 打开浏览器。浏览器页面每 30 秒发送本机心跳，页面关闭且连续 10 分钟没有请求后服务自动退出。

控制台可修改：

- `base_url`
- `allow_insecure_local_http`
- `poll_interval_seconds`
- `max_backoff_seconds`
- `android_user_id`
- `enabled`
- `device_id`
- 可选的新 `hmac_secret`

现有 HMAC 密钥永不返回浏览器。空密钥表示保持不变；填写新密钥时必须显式确认。服务端复用 runtime 配置校验，配置写入采用同目录临时文件、权限 `0600`、同步和原子替换。保存成功后创建 `run/config.changed`，短信 worker 在下一秒重新解析配置。

本地控制台使用每次启动随机生成的会话令牌。令牌存储在权限 `0600` 的状态文件中，Action 通过 URL fragment 交给页面，页面请求使用自定义 Header；服务拒绝缺失或错误令牌、非回环 Host、非同源修改请求。HTML 不包含现有密钥和短信正文。

## 兼容性

不依赖 APatch 或 KernelSU 专有 WebUI API。APatch、KernelSU 和 Magisk 都通过 `action.sh -> Android 浏览器 -> 127.0.0.1:35000` 使用同一控制台。CLI 的 `status/start/stop/revoke/rotate` 行为保持兼容。

## 验证

- 后端测试覆盖自动创建双卡空档案、保护手动手机号、历史修复。
- 前端测试覆盖两张卡分别编辑、下一空槽位、新消息自动刷新。
- Go 测试覆盖回环监听、令牌鉴权、密钥不回显、配置原子更新和空闲退出。
- Shell 测试覆盖可中断等待、配置热重载和 Action 打开控制台。
- 构建 0.2.5 模块并在当前 APatch 双卡设备上验证两张卡、控制台保存和短信延迟。
