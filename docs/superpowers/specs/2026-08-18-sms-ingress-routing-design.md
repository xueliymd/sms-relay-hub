# 短信采集、号码识别与路由闭环设计

## 目标

把当前项目从“具备上传协议和部分客户端骨架”补齐为可真实使用的短信中转系统：

- Android Root 设备仅安装 Magisk、KernelSU 或 APatch 模块，不内置 APK；
- Android 非 Root 设备安装 APK，通过系统短信广播采集短信；
- iOS 越狱设备可选择插件/守护进程直接采集，非越狱设备使用快捷指令；
- 客户端自动采集发送方、正文、接收时间和可取得的 SIM/订阅信息；
- 平台把设备、SIM 槽、订阅标识和接收手机号解析为统一接收身份；
- 管理员可以按接收手机号、发送方、关键词和验证码状态查询、领取与分流；
- 重启、重复广播、断网和临时服务端故障不得造成短信丢失或重复入库。

第一阶段以已连接的 Xiaomi M2011K2C、Android 12、arm64、APatch Root 设备完成真实端到端闭环。后续兼容性通过能力探测和设备矩阵扩展，不能把未经验证的设备宣称为已支持。

## 已确认事实

### 现有工程

- 后端已有设备凭据、HMAC/Bearer 鉴权、nonce 防重放、幂等入库、短信加密存储、OTP 解析与 claim、设备生命周期和 SIM profile 基础能力；
- Android 非 Root 工程已有 `SMS_RECEIVED` 接收器、加密 Room 队列、WorkManager、HMAC 上传和订阅快照代码，但尚未在当前机器构建 APK 或完成真机验收；
- Android Root 模块已有配置校验、签名上传、原子 claim、spool、quarantine 和重试骨架，但没有实际短信读取器；
- iOS 快捷指令已有请求契约和文字说明，但操作步骤过于复杂，缺少可照着完成的图文教程；
- iOS Ve 适配器当前采集 MobileSMS bulletin，不等于现代越狱环境下直接读取短信数据库；
- 管理台已有设备和 SIM profile 操作，但尚未完成按接收手机号、发送方与规则的短信分流工作台。

### 已连接 Android 真机

- Root 可用，模块运行于 Root 管理器提供的高权限域；
- `content://sms/inbox` 可返回 `_id`、`date` 和 `sub_id`；
- 系统包含 `/system/bin/inotifyd`；
- Telephony 数据库位于标准 device-encrypted 路径；
- Xiaomi 的 `sms` 表包含 AOSP 基础列，并扩展了 `sim_id`、`sub_id`、`deleted`、`block_type` 等字段。

以上事实证明纯 Root 模块可行，但不证明其他 ROM 已完成验收。

## 参考项目与使用边界

### Android

- `pppscn/SmsForwarder`：参考非 Root APK 的短信监听、规则模型、出口管理、日志和保活；不复制其产品架构，也不把 App 当作 Root 模块；
- `zgcwkjOpenProject/Magisk_SmsForwarder`：参考 Root 下通过 Telephony Content Provider 读取短信的可行性；不复用其内存游标、明文日志和直接第三方出口设计；
- `GaoChX/sms-forward-magisk-module`：参考数据库/WAL 变更监听、持久游标和低功耗守护；不写死单一路径、单一 ABI 或 Telegram 出口。

### iOS

- `Thesaru-p/sms_automation`：参考“信息自动化 -> 获取 URL 内容 -> POST Shortcut Input”的简化教学顺序；实际请求继续使用当前平台的设备鉴权和幂等协议；
- `evianzhow/iForward`：仅参考越狱环境读取 `sms.db` 的架构证明；其数据库 schema、启动方式和邮件出口过旧，不直接复用。

### 合宙/LuatOS 参考包

用户提供的压缩包只作为协议语义参考：设备注册、心跳、短信事件、命令和响应。不得执行或复用其中的 LSPatch/DCloud 包装 APK、硬编码共享凭据、明文短信日志，以及解密后执行 `eval` 的 PHP 文件。

## 总体架构

所有采集端输出统一的标准短信事件，平台只维护一套 ingest、幂等和路由逻辑。

```text
Android Root 模块 ─┐
Android 非 Root APK ├─> 标准短信事件 -> 设备鉴权 -> 幂等入库 -> 接收身份解析 -> 查询/OTP/路由
iOS 越狱插件 ──────┤
iOS 快捷指令 ──────┤
SIM 板/CPE 驱动 ───┘
```

标准事件至少包含：

- `event_id`：客户端稳定事件 ID；
- `source`：`root_module`、`android_app`、`ve_tweak`、`ios_shortcut` 或 `sim_board`；
- `sender`；
- `body`；
- `received_at`；
- `sim_slot`，无法取得时为空；
- `metadata.subscription_id`，无法取得时省略；
- `metadata.carrier_name`，无法取得时省略；
- `metadata.phone_number`，只有系统或设备可靠返回时才发送；
- `metadata.source_message_id`，用于客户端重启后的稳定去重。

服务端不能把客户端上报的手机号直接当成已验证身份。最终接收手机号通过设备 SIM profile 解析；自动值和手工值冲突时保留冲突状态，由管理员确认，不静默覆盖手工映射。

## Android Root 模块

### 约束

- 模块本身完成短信读取、队列、签名和上传；
- 不安装、不启动、不依赖任何 APK；
- 不修改短信的已读、已查看、删除或归档状态；
- 不在日志中输出正文、完整发送方、手机号、设备密钥或服务端响应正文；
- 不把 ROM 名称或手机型号作为首要分支条件。

### 读取策略

采用 Provider 优先、事件唤醒、数据库兜底的混合方案。

1. 启动时探测 `content://sms/inbox` 是否可读，并逐项探测可用列；
2. Provider 可用时，以递增 `_id` 为主游标读取新收到的 SMS，只处理收件箱记录；
3. 使用 `inotifyd` 监听已发现的 Telephony 数据库及 WAL/SHM 文件变化，收到变化后触发扫描；
4. 无变化时仍进行有上限的周期补偿扫描，修复漏掉的文件事件；
5. Provider 不可用或输出无法无损解析时，进入数据库兜底；
6. 数据库兜底先发现候选路径，再检查 `sms` 表和列，不假设固定 ROM schema；
7. 查询结果使用安全编码输出，正文中的换行、逗号、等号和非 ASCII 字符不得破坏记录边界；
8. provider 和数据库游标分别持久化，切换来源时不得重复上传已确认事件。

### 事件 ID 与状态

`event_id` 由设备 ID、数据源类型、源消息 ID、接收时间和内容摘要共同派生。Root 私有状态目录权限必须为 `0700`，游标和 claim 使用同目录临时文件加原子重命名写入。

新事件先写入 spool，再尝试上传。只有服务端确认接受或确认幂等重复后才能清理本地事件。可重试错误保留队列并指数退避；永久配置错误停止上传但不丢队列；格式损坏事件进入 quarantine，并只记录事件摘要和原因。

### SIM 与接收手机号

- 优先采集短信行上的 `sub_id`、`sim_id` 或等价字段；
- 通过系统订阅能力映射 SIM 槽和运营商；
- 系统能可靠返回本机号码时作为 `auto` profile 候选；
- 无法返回号码时短信仍正常上传，由管理台手动绑定槽位/订阅与手机号；
- 双卡设备无法判断某条短信的订阅时，标记为 unresolved，不得随意选择 SIM 1。

## Android 非 Root APK

非 Root APK 使用系统 `SMS_RECEIVED` 广播读取 PDU，并沿用现有加密队列和 WorkManager 上传。需要补齐：

- 首次启动配置和设备绑定界面；
- 短信、通知、电池优化等必要权限的可操作状态提示；
- 重复 PDU、分段短信、双卡 subscription hint 和设备重启的测试；
- 构建可安装 APK，并在至少一台非 Root 真机完成真实短信到平台验收；
- 权限被拒绝或后台被限制时明确显示错误，不把“已安装”显示为“正在接收”。

Root 和非 Root 客户端不得同时采集同一台设备，除非管理员显式启用双源迁移模式；服务端仍以 `event_id` 和内容幂等键抑制重复。

## iOS 接入

### 非越狱快捷指令

快捷指令依赖 iOS“信息”个人自动化：收到符合条件的信息后立即运行上传动作。它不具备后台数据库扫描能力，因此：

- 发送方、正文和触发时间从 Shortcut Input 获取；
- 接收手机号通常无法可靠自动读取，创建设备时必须选择或手动填写号码；
- 自动化过滤条件只负责触发范围，平台规则负责最终 OTP/关键词路由；
- 教程必须从空白自动化开始逐屏说明，不要求用户手写签名算法；
- 在真实 iPhone 请求成功前，不生成可能误导用户的最终 PPT。

### 越狱插件/守护进程

越狱端作为快捷指令的可选替代，使用现代越狱环境可访问的 MobileSMS 数据源，并共用 HMAC、spool、幂等和 SIM profile 协议。实现需要区分 rootful/rootless 路径和实际 iOS schema；无法证明兼容的版本必须列为未验证，不沿用旧 iForward 的硬编码 schema。

## 平台接收身份与路由

### 接收身份解析

服务端按以下优先级解析每条短信的接收身份：

1. `device_id + subscription_id` 的已确认 SIM profile；
2. `device_id + sim_slot` 的已确认 SIM profile；
3. 客户端自动发现且尚未冲突的手机号候选；
4. 单 SIM 设备唯一的手工 profile；
5. 无法解析时标记 unresolved，短信仍可见和可查询。

### 查询与状态

管理台和脚本 API 至少支持：

- 按接收手机号、设备、SIM 槽、发送方、关键词、时间范围筛选；
- 全部短信、未读、仅验证码、待领取和已领取视图；
- 短信 read/unread 状态与 OTP available/claimed/expired 状态分离；
- JSON 和纯文本方式读取验证码；
- claim 操作保持原有一次性领取和并发安全语义。

### 路由规则

第一版规则条件包含接收手机号、设备、发送方和正文关键词/正则；动作包含保留、标记 OTP 和调用已配置出口。默认策略是接收入库后再过滤，设备端只提供可选的明确 allow/deny 规则，避免错误配置导致不可恢复的短信丢失。

## 安全与隐私

- Root、Android App、越狱插件和卡板使用设备级 HMAC；快捷指令继续使用可轮换的设备 Bearer 凭据；
- 服务端继续校验时间戳、nonce、正文摘要和设备状态；
- 所有客户端凭据只能存放在客户端私有配置中，示例文件不得包含真实凭据；
- 本地队列和服务端数据库中的短信正文继续加密或受 Root/应用沙箱保护；
- 日志只允许记录事件 ID 摘要、状态码、重试次数和脱敏错误；
- 用户提供参考包中的共享 MQTT 密钥、服务器地址和短信内容不得复制进代码或文档。

## 错误处理

- 读取能力缺失：记录具体探测失败项并停止假成功状态；
- 字段缺失：省略可选 metadata，不阻塞短信正文上传；
- 接收号码未知：标记 unresolved，允许后台补映射；
- 网络失败和 5xx：保留队列并退避重试；
- 401/403 或设备撤销：停止发送、保留队列，等待新凭据；
- 409 幂等重复：视为已送达并清理本地事件；
- 4xx 永久载荷错误：进入 quarantine，不无限重试；
- 本地队列达到容量上限：停止删除旧事件，显示明确告警并拒绝静默丢弃。

## 分阶段交付

### 第一阶段：Root 真机闭环

- 完成纯 Root reader、事件唤醒、补偿扫描、SIM metadata 和持久游标；
- 在已连接 Xiaomi 手机上配置真实测试设备；
- 验证收到短信、平台可见、API 可读、重启不重复、断网补发；
- 同时修正管理台的接收号码解析和 unresolved 展示。

### 第二阶段：非 Root APK 与平台路由

- 建立 Android 构建工具链并产出 APK；
- 完成非 Root 真机权限、广播和后台上传验收；
- 补齐按接收手机号、发送方、关键词和 OTP 状态的查询与规则。

### 第三阶段：iOS

- 先完成并实测最简快捷指令流程；
- 基于实测界面制作完整中文图文 PPT；
- 再按实际越狱环境实现和验证插件/守护进程。

### 后续阶段：SIM 板、CPE 与热点设备

保留统一设备注册、心跳、短信事件和命令响应驱动接口。没有明确厂商、型号和 API 时不承诺兼容；LuatOS 可优先参考合宙包的事件语义，但必须改为设备独立凭据、TLS/HMAC 和脱敏日志。

## 测试与验收

### 自动化测试

- Root：能力探测、Provider/数据库解析、特殊字符正文、持久游标、inotify 唤醒、补偿扫描、spool、重试、quarantine 和停止生命周期；
- Android App：PDU 解析、分段合并、重复广播、订阅快照、加密队列、Worker 重建和 HMAC；
- 后端：接收身份优先级、profile 冲突、unresolved、查询筛选、read/unread、OTP 状态和并发 claim；
- 前端：SIM 映射、unresolved 告警、筛选、规则编辑和状态操作；
- iOS：快捷指令请求契约和越狱客户端签名向量。

### 真机门禁

第一阶段必须保留一次真实链路证据：

1. 发送测试短信前记录平台计数；
2. 手机实际收到短信；
3. Root 模块产生单一稳定事件；
4. 服务端接受并显示正确发送方、时间和接收 SIM；
5. API 返回同一短信或 OTP；
6. 重启模块后没有重复；
7. 断网期间收到的新短信在恢复网络后补发。

测试证据必须脱敏，不在日志和文档中保留真实验证码、完整手机号、设备密钥或短信正文。

## 非目标

- 第一阶段不实现卡板厂商专用驱动；
- 不安装或执行用户参考包中的 APK/PHP 服务；
- 不保证所有 Android/iOS 版本在未经真机验证时可用；
- 不把教程、截图、PPT 或安装成功当作短信端到端验收；
- 不改变手机原短信的已读、删除或归档状态。
